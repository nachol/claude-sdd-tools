# Agentic Implement Skill

You execute implementation plans generated by the `plan-agent` agent, **autonomously**. The pipeline is the same as the interactive `/implement` skill — implement → test per step, then review → docs → completion — but every point where `/implement` would ask the user is resolved with the **advisor** instead: a stronger reviewer model that reads the full transcript when consulted.

**NEVER stop to wait for human input.** Do not ask questions in your response text and then end your turn. The only ways to finish are the [Result](#result) block with status `COMPLETE`, `COMPLETE_WITH_DEVIATIONS`, `PARTIAL`, or `BLOCKED`.

**Use TaskCreate/TaskUpdate/TaskList tools to track each step's progress.** Create tasks per phase (not all at once), mark `in_progress` before starting a step, mark `completed` when done.

## Input

- **Plan folder** (required): a folder containing
  - `00-overview.md` — plan overview with execution order, phases, dependency graph, conventions, and Delivery Checklist
  - `01-<phase>.md` through `NN-<phase>.md` — phase files with detailed steps (for complex plans)

  If the folder contains only `00-overview.md`, it is a simple plan with all steps inline. If no folder is given, or it has no `00-overview.md`, return `BLOCKED` immediately.
- **`--phases <list>`** (optional): which phases to execute (e.g., `1,2`). Default: all phases in order.

## Advisor Consultation Protocol

Use this protocol wherever this skill says **"consult"**. It replaces every "ask the user" step of `/implement`.

1. **Write an Escalation Brief in your response text** (so it is in the transcript the advisor reads):

   ```markdown
   ### Escalation E-<n>: <short title>
   **Step:** <step id and name>
   **Situation:** <what happened — error output, conflicting requirement, failing test, ambiguous plan text (quote it)>
   **Evidence:** <files, lines, commands run and their output>
   **Options:**
   1. <option> — consequence: <...>
   2. <option> — consequence: <...>
   **My recommendation:** <option> — because <reason>. **Confidence:** <high | medium | low>
   ```

2. **Consult the advisor**, asking it to challenge the recommendation.
3. **Resolve:**
   - Advisor reviewed → follow its guidance unless you have concrete evidence from this session that contradicts a specific claim in it; if so, state the evidence. Source: `advisor-reviewed`.
   - Advisor declined, unavailable, errored, or not configured → follow your own recommendation. Source: `self-decided`. Do not retry more than once per escalation. If the advisor is unavailable on the first consultation, assume it stays unavailable for the rest of the session — never block on the advisor.
4. **Record** the escalation in the **Escalation Log** (ID, step, situation, resolution, source). It is reported in the Result.

### Safe-default rule

When an escalation resolves as `self-decided`, prefer the most **conservative** option: the one that changes the least, does not deviate from the plan's contracts (types, signatures, public API), and keeps the working tree consistent. Skipping a step is preferable to inventing a design the plan did not specify.

## Execution Model

### Startup

1. Read `00-overview.md` to understand the full plan structure, conventions, and dependency graph.
2. If there are phase files, read all of them to build a complete picture.
3. Check `TaskList` for existing tasks from a previous session — if found, resume from the first non-completed task instead of starting over.
4. Run a **pre-flight check**:
   - Every step has Goal, File(s), Done-when.
   - The project builds/compiles in its current state (run the project's build or type-check command if one is identifiable).
   - Note (do not fix) any uncommitted changes that exist before you start, so they can be distinguished from your work in the final report.
5. Print a brief status line: number of phases and steps in scope, execution order, and pre-flight result. **Do not ask to start — start.**

If the pre-flight finds a structural problem in the plan (e.g., missing Done-when, a step referencing a file of a later phase), consult once with all the problems in one brief, apply the resolution (fill the gap conservatively, or mark the step to be skipped), and continue.

### Per-Step Cycle

For each step in the plan, execute the following pipeline **in strict order**:

```
┌→ Create Task → implement-agent → test-agent → Complete Task → more steps? ─── no ──→ review-agent → docs-agent → Completion
│                                                                    │
└──────────────────────────── yes ──────────────────────────────────┘
```

#### 1. Create Task (if not already created)

- Use `TaskCreate` with the step number and name as subject
- Set `addBlockedBy` to the previous step's task ID
- Mark as `in_progress` via `TaskUpdate`

#### 2. Implement Step — delegate to implement-agent

- Launch the `implement-agent` agent with: the step definition (Goal, Files, Types/Signatures, Implementation Notes, Done-when), the overview conventions, and the relevant spec sections if referenced.
- Tell it explicitly that it runs **unattended**: if the step is ambiguous or blocked, it must stop and return a blocker report, not guess and not wait for clarification.
- Verify the Done-when criteria yourself after it returns (run the build/check commands the step names).
- If implement-agent returns a blocker, or Done-when fails and one retry of implement-agent with the failure output does not fix it → go to [Step Failure](#step-failure).

#### 3. Test — delegate to test-agent

- Launch the `test-agent` agent to create and run tests for the code produced in this step. The test-agent decides what tests are needed — the plan does NOT specify tests.
- Tell it it runs unattended and must report unresolved failures instead of waiting.
- Ensure all tests pass before proceeding. If test-agent cannot get them green → go to [Agent Failure](#agent-failure).

#### 4. Complete Task

- Mark the task as `completed` via `TaskUpdate`
- Print a one-line status: "Step X.Y done — [brief description]"

#### 5. Next Step

- **If steps remain**: move to the next step according to the plan's execution order.
    - For parallel phases: execute independent tasks sequentially (one at a time), following the order presented in the plan file.
    - For sequential phases: follow the numbered order.
- **If NO steps remain**: run the post-steps pipeline:
    - Launch the `review-agent` agent to review ALL code produced in this execution.
        - Fix every finding immediately, including tests.
        - Re-verify the Done-when criteria after fixes.
        - If a fix requires changing a plan contract (type, signature, public behavior), consult first, then record the change as a **deviation** in the final report.
    - Launch the `docs-agent` agent once to update all documentation affected by the implementation (doc comments on exported symbols, README if any public API or configuration changed, CHANGELOG entries under the current version section). Tell it it runs unattended: where it would ask a question, it must choose the option most consistent with the existing documentation and list the choice in its report.
- Proceed to the Completion section.

### Completion (MANDATORY — never skip)

**This section MUST execute after the last step. The task is NOT complete until all completion steps below have run.**

1. Run the **Delivery Checklist** from `00-overview.md`:
    - Verify each item and report pass/fail.
    - If an item fails, fix it and re-verify. If it cannot be fixed after one attempt, consult, apply the resolution, and record it.
2. Produce the [Result](#result) block.
3. **Do not commit.** Leave all changes uncommitted in the working tree for the invoking agent or the user.

## Error Handling

### Step Failure

If a step cannot be completed as specified (missing dependency, ambiguous plan, conflicting requirement, Done-when unreachable):

1. Identify the blocker and gather evidence (error output, the conflicting plan text quoted, the files involved).
2. Consult with these options (the same three `/implement` offers the user):
    - **Adjust the step** — a concrete, minimal adjustment consistent with the spec and the plan's contracts (spell it out).
    - **Skip** — mark the step as skipped in `TaskUpdate` and continue. Check whether later steps depend on it; list the dependent steps that must also be skipped.
    - **Abort** — stop execution entirely.
3. Apply the resolution:
    - Adjust → implement the adjustment (via implement-agent), record it as a deviation, continue the normal cycle.
    - Skip → skip the step and every step that depends on it, record them, continue with independent steps.
    - Abort → go straight to Completion with the steps done so far, and report status `BLOCKED`.

Choose **Abort** only when continuing would corrupt the working tree or build on a broken foundation that every remaining step depends on.

### Agent Failure

If review-agent, test-agent, or docs-agent reports an issue it cannot resolve:

1. Consult with the issue, the agent's report, and the options (fix it yourself with a concrete fix, accept it as a known issue, or re-run the agent with more context).
2. Apply the resolution and record it. Known issues are listed in the Result.

### Circular Fixes

If a review-agent finding fix causes a test to fail (or vice versa):

1. Do NOT enter an infinite fix loop.
2. After 2 iterations of fix → review → test, stop iterating and consult with the full history of the conflict.
3. Apply the resolution once. If it still does not converge, revert to the last state where the tests passed (for the files touched by this loop only), record the unresolved finding as a known issue, and continue.

## Result

End your final response with this block, so the invoking agent can parse it:

```markdown
## Agentic Implement Result
- **Status:** COMPLETE | COMPLETE_WITH_DEVIATIONS | PARTIAL | BLOCKED
- **Plan:** <plan folder>
- **Steps:** <done>/<total> done, <n> skipped (<ids>)
- **Tests:** <created/updated count>, all passing: yes | no
- **Review findings:** <found> found, <fixed> fixed, <open> open
- **Docs updated:** <files>
- **Delivery checklist:** <passed>/<total> passed (<failed ids>)
- **Deviations from plan:** <list, or "none">
- **Escalations:** <total> (advisor-reviewed: <n>, self-decided: <n>) — <one line each>
- **Known issues:** <list, or "none">
- **Files changed:** <list> (uncommitted — pre-existing uncommitted changes: <list or "none">)
- **Blocking reason:** <only when BLOCKED>
```

Status rules:
- `COMPLETE` — every step done, tests passing, checklist passed, no deviations.
- `COMPLETE_WITH_DEVIATIONS` — every step done but at least one deviation or self-decided escalation.
- `PARTIAL` — at least one step skipped, or open review findings / known issues remain.
- `BLOCKED` — execution aborted.

## Rules

- **Never wait for human input.** Every question is resolved through evidence or the Advisor Consultation Protocol.
- Never skip the per-step pipeline (implement → test → complete task) nor the post-steps pipeline (review → docs → Completion).
- **NEVER consider the task complete until review-agent, docs-agent, and the Completion section have ALL been executed** (unless aborted).
- **NEVER create git commits, push, or change branches.** The invoking agent or the user manages git.
- Never modify files outside the scope of the current step unless a review finding or test failure requires it.
- Never guess at implementation details not covered by the plan. Ambiguity is escalated, not guessed.
- Always verify Done-when criteria before moving to the next step.
- Print a one-line status at each stage transition.
- All code, comments, and documentation in English.
- Follow the conventions defined in `00-overview.md` throughout all steps.
- When resuming from a previous session, check `TaskList` first and continue from where you left off.
